● I now have enough grounding to propose the actual design. One more
  architectural fork worth flagging before I write it up: the real POS checkout
  today creates a Bill (not Order/Invoice — those exist but aren't what POS
  uses), and Bill already has status: INITIATED → DRAFT → COMPLETED and even an
  EPaymentMethod.CREDIT value sitting unused. That changes the cleanest path
  forward.

  Proposed approach: extend Bill, don't build a parallel Sale entity

  Add columns to BillEntity (saleType, customerType, paymentTiming,
  isBlack/black amount/commission fields) rather than introducing a new domain
  object. This reuses the entire existing checkout flow, POSTerminal.tsx, Bills
  list/detail, and the print pattern already built — versus a new parallel
  entity that would duplicate all of that for no real gain. I'm confident in
  this one and would only reconsider it if you want Sales kept structurally
  separate from Bills for some reason I'm not aware of.

  Design

  Data model
  - Bill: + saleType (normal/credit/black), customerType (regular/new/shop/big),
  paymentTiming (before/after/half/COD), heldAt reuses existing DRAFT status (a
  bill sitting in DRAFT is the "Rakhone" hold list — no new status needed),
  blackAmount, facilitatorUserId/facilitatorName, commissionAmount.
  - Customer: + creditLimit, creditBalance (running balance) + a new
  CustomerCreditTransaction ledger table (mirrors the StockMovement pattern
  already used elsewhere) for audit trail.
  - CreditApprovalRequest: new, simple table (product-specific generic approval
  engine is YAGNI here — nothing else needs it yet) — customer, requested
  amount, requested-by, status, approved-by.
  - UnpublishedStock repurposed as the black pool: role check tightened per your
  answers (Store Manager/Staff: view+add for their own location; sale creation
  restricted to OrgAdmin/OrgManager/SuperAdmin only).
  - CommissionPayable: new ledger table — facilitator (user ref or free-text),
  amount, paid flag.
  - ERole: add OrgManager, equal permissions to OrgAdmin everywhere
  black/credit-approval is checked.

  Sales screen (POSTerminal.tsx v2)
  - Sale-type toggle: Normal / Credit / Black (Black option hidden unless role
  is OrgAdmin/OrgManager/SuperAdmin).
  - Customer type row (Regular/New/Shop/Big Customer) — label only, independent
  of sale type.
  - Inline customer fields (existing edit pattern) + credit limit/balance shown
  when Credit selected.
  - Payment method (existing) + new payment-timing field; "half" is a free-entry
  amount.
  - Hold ("Rakhone") button saves the bill in DRAFT and returns to it later from
  a Held Sales list.
  - On Black: seller enters the charged price per line; system computes
  blackAmount = charged − official automatically; stock deducts from the black
  pool (official count untouched); optional facilitator + commission %.
  - Debtor Note / Statement / Delivery Note: window.print-based documents, same
  pattern as ReceiptDocument.tsx.

  Credit flow: sale total > (creditLimit − creditBalance) → blocked, creates a
  CreditApprovalRequest; OrgAdmin/OrgManager see it in a Pending Approvals list;
  approve → sale proceeds and creditBalance rises; payments against a customer
  reduce creditBalance.

  Explicitly out of scope for this cycle (separate future cycles, per our

  reporting suite beyond what's needed to see credit/black activity, real
